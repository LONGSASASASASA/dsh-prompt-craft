# 意图优先的提示词增强：方案 B

状态：用户于 2026-11-21 确认方案 B，已进入实现。
日期：2026-11-20

## 目的与优先级

把“替用户重新定义目标”改为“忠实表达用户已经给出的意思”。用户反馈现有输出不自然，目标强化、立意升维与强制经验规则会偏离本意。

优先级：忠实原意 > 自然可读 > 必要的清晰度 > 简洁。不得以专业、升维、可验收为由新增用户未授权的要求。

## 方案选择

A：每次确认目标后改写，方向稳但每次多一步。B：仅在有关键歧义时澄清，明确时直接改写，快但依赖判断。用户选择 B。

不采用继续叠加规则模板的方案：来源可信并不意味着每条规则都适用于本次需求。

## 行为设计

### 明确输入：直接改写

点击增强后一次调用完成意图检查与改写；没有影响方向的缺口则直接显示结果，不增加确认点击。只修歧义、语序与重复，保留用户语气和明确约束。已经清楚的文本可以原样返回，并说明无需修改。

“目标”仅复述用户明示内容，标签改为“本次理解”；不宣称掌握用户未表达的真正目标。用户可通过现有继续改稿入口纠正理解。

### 关键歧义：先问再改

以下缺口需要澄清：缺少可从当前草稿与相关用户历史确定的对象；存在会导向不同交付物的多种解释；明确要求互相冲突；改写必须替用户决定重要取舍或扩大范围。

缺少技术版本、具体文件名不必一律提问：若执行者可从项目中查明，保留自然指代或要求先定位，不编造文件、不堆占位符。

每轮最多一个关键问题。问题简短中性，不预设答案，不把模型推测写成事实。回答后重新检查原草稿加补充信息，仍有关键歧义才继续问；允许用户随时退出，不形成强制问卷。

现有“按缺省值直接改”入口改为“仅润色原文”：不替用户猜答案、不补目标、不扩范围；允许保留尚未解决的歧义。

### 自然语言与建议

取消强制文言、固定章节、每次必须立意升维的要求。短输入不套完整工程流程，非编码场景不套 coding-agent 规则。保持默认对比与分段接受、应用和撤销不变。

非必要建议默认不生成；有实质价值时才单独展示“可选建议，未加入正文”。建议只有用户明确接受后才能进入改写，现有分段接受不能被当成对未展示建议的授权。

## 内部判断线索

借鉴需求访谈的复述确认与 Jobs to Be Done 的“情境—行动—期望结果”视角，仅作内部检查线索，不把栏目强加给用户，不把它们称为已验证的目标识别算法。实现前核对一手框架来源，不能凭框架权威替用户作决定。

区分用户明示事实、相关历史、模型推测。历史助手建议不是用户承诺；用户最近明确纠正优先于旧推测。若当前上下文投影无法证明用户接受某项建议，不将其写进要求。

## 实现边界

复用现有 enhanced/questions 分支、回答追问与继续改稿流程。调整 host 模板与规则适用范围、必要的协议字段和解析、客户端文案与建议展示。公开经验保留为按需使用的表达参考；规则引用只是来源说明，不是改写忠实度证明。

不改主题、停靠对齐、微信桥、模型配置、默认对比及应用撤销行为。不在本设计审批前写产品代码或发布。

## 验收

- 明确需求直接出稿，无额外确认；原意与每条硬约束保留，零未授权交付物。
- “把登录页改高级一点”先澄清视觉含义，不自行指定毛玻璃、注册或社交登录。
- “修复此错误，不要重构”不加入架构改造；能够定位对象时不重复问文件名。
- 简单文字润色不增加测试、计划、验收清单等工程模板。
- 历史助手曾建议 Redis、用户未接受：新稿不得把 Redis 写成既定要求。
- 用户否定本次理解后，后续稿遵循纠正，不固守之前推断。
- 仅润色入口不暗中选择默认目标或补需求；可选建议不混入正文。
- 允许不改、允许不产生升维说明、允许没有规则引用。
- 自动测试覆盖分流、纠正、历史污染与范围约束；真实模型样例另做人工语义核对，测试全绿不等于自然语言永不跑偏。

## 剩余实现裁量

开发者可决定最小协议字段与组件拆分，遵循既有 class/slot 契约与 useComposerAlign；不新增独立服务或依赖。若需要改变以上用户体验，回到设计确认。
